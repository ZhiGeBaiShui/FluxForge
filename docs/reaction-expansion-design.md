# FluxForge 反应装置扩展评审

> 2026-11-04 · 设计评审，不是实现承诺
>
> 参与身份：创意总监 / 化学反应系统 / 技术架构 / 经济平衡 / 红队可理解性。
> 结论基于当前仓库与反编译事实；涉及原版价格、客户需求、瓶内 `ChemicalHelper` 行为的数字均标记为待验证假设，不当作已证实事实。

---

## 0. 一页结论

### 不要做“第二套化学引擎”

游戏本体已经有：

```text
ChemicalHelper 的逐 tick 化学反应
加热板 / 蒸发器 / 成型机
水质等级、纯度、致死性、欣快、成瘾
客户、试纸、黑市、医疗、声望
```

FluxForge 的价值不是再写 15 条配方，而是：

> **把原本要过夜、要整台机器的化学，压缩进柜台后的一根管子；让玩家看见顺序，承担后果，并让顾客记住。**

所以推荐：

```text
反应装置只做“中间体 / 预处理 / 分离”
最终成型、定价、销售、后果继续交给原版系统
```

### 最大惊喜 Top 3

| 排名 | 反应 | 惊喜点 | 为什么不是第一个做 |
|---:|---|---|---|
| 1 | **芬太前处理（脱稳定剂）** | 最明显的配方是错的；稳定剂是锁；紫色产物；近致死剂量 | 依赖酸/过滤/还原/高温/原版成型机，链路最长 |
| 2 | **冷萃（梦帽菇酒精萃取）** | 40–60°C 只有几秒窗口；冰会稀释；“越冷越纯”是错的 | 现有函数产率/溶剂条件需要先修 |
| 3 | **氯洗** | 最清的水可能最化学；顾客试纸拆穿“看起来干净” | 依赖水质等级与客户检测，价值出口未验证 |

### 推荐建造顺序

```text
P0  冷萃 / 溶剂萃取垂直切片
    一个 chem_reactor + 三条萃取规则（咖啡 / 梦帽 / 梦魇）
    无状态、无新 flow tag、复用现有纯函数

P1  氯洗 + 中和 + 过滤
    验证“水质等级 / 顾客试纸 / 废物处理”这条社会后果链

P1  芬太前处理（脱稳定剂）
    只处理甲基醇的稳定剂锁，最终芬太仍由原版机器完成

P2  发酵 / 精馏 / 稳定化 / 热解 / 氰化
    需要批次状态、多出口 router、危险系统
```

**先做 1 条垂直切片，不是 10 台机器。** 当前的 UI、存档和价值出口还不足以让第 4 条反应被理解。

## 1. 硬约束：先承认这些事实

### 1.1 反应是“单帧点修饰”，不是反应器

`FlowManager.TryProbeCell`：

```text
reactor.TryReact(properties)
  → true: StopAt(cellX, cellY)
  → 下一帧从下一格继续
```

因此：

```text
没有 dt
没有停留时间
没有逐 tick 反应
没有装置内排队
一次经过 = 一次批量反应
```

任何“发酵 2 天”“连续搅拌”“按秒转化”的设计，都不能直接套 `IFlowDevice`。

### 1.2 在途物质不存档

`FlowRuntime.Emit` 先把液体从物品 tag 清零，再把 `FlowEntity` 放进内存；`SaveGame` 只保存物品 tag，`SaveLoaded` 会 `KillAll`。

```text
发射后、流源还在网格里时保存
  → 读档后整批物质消失
```

这是 S1 数据丢失路径。**在加入高价值多步反应前必须解决**，否则反应链越长，损失越贵。

可选策略：

1. 保存时提交到最近收集器 / 发射源；
2. 保存时退还来源容器；
3. 有在途流源时禁止保存，并明确提示。

### 1.3 物种封闭

当前只有 36 种液体 + `container_temp`。没有压力、pH、气体、盐。

```text
输出必须是现有 36 种液体之一
不新增 flow tag
不把“充能/次数”塞进 FlowPropertyRegistry
```

“盐/气体/沉淀”需映射到 `mineral`、`debris`、`chemical_contaminant` 等现有 tag。

### 1.4 原版已经有同一批反应

原版 `ChemicalHelper` 已经处理酸碱、氯、有机废物、梦帽菇萃取等。

必须有一张 **反应归属矩阵**：

```text
每个液体对只能有一个 owner
  device 或 vanilla
不能两边都跑
```

FluxForge 优先做原版没有的：

```text
连续流动预浓缩
温度窗口内的顺序控制
在线分离/过滤
把预处理压缩到几秒
```

而不是把原版配方抄一遍、做得更快更便宜。

### 1.5 当前 UI 支持不了“很多配方”

- tooltip 只显示水和温度；
- 36 种液体中 17 种共享 4 个 RGB；
- 反应格被装置贴图遮挡；
- 没有配方书、没有失败原因、没有装置状态；
- `TryReact` 失败时流源直接穿过，玩家不知道为什么。

在补 UI 之前，**最多 3 个简单配方**。

## 2. 玩家幻想与三根支柱

### 一句话幻想

> 我是这条街上唯一知道液体刚才流过什么的人：我把一夜的化学压进一根管子，然后把它卖给一个只看标签的顾客。

### 三根支柱

| 支柱 | 感觉 | 机制 | 可观察测试 | 反目标 |
|---|---|---|---|---|
| **管子会说话** | 不用打开面板，我就知道它在反应 | 颜色/浊度/粒子/停顿/残留；装置状态 | 给没读过文档的玩家看 3 秒，能说出“在加热 / 在反应 / 卡住了 / 过去了” | 只有 tooltip 数字变化，画面没变 |
| **顺序就是配方** | 同样原料，换一种接法就是另一门生意 | 温度窗口、冰稀释、串联/分流/回流 | 两组相同原料、不同布局，产出不同等级/产品，且店内可发现 | 一台机器一个“制作”按钮 |
| **后果有脸** | 每批货最后都会坐到我对面 | 纯度/意图/致死性进入试纸、退货、声望、检查 | 一批货能追到具名顾客，并改变价格/声望 | 产物只变成 +X 金币 |

优先级：**管子会说话 > 顺序就是配方 > 后果有脸**。

先看见，才相信；先相信，才排列组合；先排列组合，才把后果带到柜台。

## 3. 惊喜曲线：管子记得 → 顾客记得 → 店铺记得

随机性不是惊喜，记忆才是。

### 0–30 分钟：管子记得

```text
第一次停顿：水流在反应器格停了一下
  → “它在想。”

第一次变清：浑浊变透明，但试纸显示纯度没变
  → “我骗过了眼睛，没骗过试纸。”

第一次等级跃迁：脏水过氯，水级从铁锈水变成基础水
  → “1% 的纯度就是一个社会阶层。”

第一次残留：反应器内壁留下上一批的膜
  → “它记得上一批。”
```

### 中局：顾客记得

```text
批量买家带试纸
  → 你的“基础水”其实是 97.8% 的幽灵水
  → 交易失败，他告诉别人

成瘾者买了梦尘
  → 第二天手note 说睡了个好觉
  → 或者开始戒断

梦魇提取液卖给平民
  → 赔偿 / 声望 / 调查
  → “最赚钱的配方是最脏的。”
```

### 后期：店铺记得

```text
夜班：你不在时，反应器把一批货做完了/做坏了
双用途：同一套管路，换一个试剂盒，从梦尘切到梦魇尘
签名：你给一批货命名，顾客开始点名要“那瓶粉的”
```

**关键：每个阶段的“倒吸一口气”都不是爆炸，而是被看见。**

## 4. 三个签名反应

### 4.1 冷萃：梦帽菇酒精萃取

```text
输入：dream_cap_mush + alcohol（建议 4:1 以上）
温度：40–60°C
输出：dream_cap_extract + plant_matter
流：StopOnce
```

**玩家操作**

```text
菇糊 + 酒精 → 加热器 → 冰块 → 收集瓶 → 原版蒸发器/成型机
```

**为什么惊喜**

- 40–60°C 只有几秒窗口；超过 60°C 萃取液降解为植物质。
- 冰块降温会 1:1 化成水，**稀释产品**；它只对含水流源生效。
- “越冷越纯”是错的：颜色越浅，等级可能越低。
- 同一个反应器，梦帽菇/梦魇帽菇/咖啡豆糊都能处理；温度窗口不同。

**设计修正**

现有纯函数是一次性把全部菌糊转完、酒精不消耗、产率 50%/75%。直接接装置会变成印钞机。

P0 必须至少做一项：

```text
酒精每批损耗 10–20%
或产率上限降到 25–40%
并加入热/时间/设备成本
```

**验收**

```text
AC-COLD-1
Given: 100,000 µL 梦帽菇糊 + 400,000 µL 酒精，容器 55°C
When: 发射经过萃取反应器
Then: 产生 dream_cap_extract + plant_matter，总液体量不变；
      酒精有明确损耗；tooltip 显示温度窗口与比例要求

AC-COLD-2
Given: 同输入，温度 65°C
When: 经过反应器
Then: 萃取液降解为 plant_matter；玩家能从颜色/状态/文字知道“太热了”

AC-COLD-3
Given: 同输入，先过冰块把 60°C 降到 45°C
When: 再经过反应器
Then: 成功，但冰化水稀释产品，等级下降；玩家能解释“冷过头了”
```

**技术定位**

```text
一个 chem_reactor device key
三条萃取规则（Coffee / DreamCap / NightmareCap）
复用现有纯函数作为 kernel
P0 无状态、无新 tag、无新 patch
```

### 4.2 氯洗：干净得发苦

```text
输入：microbe / chemical_contaminant + chlorine（弹药盒）
温度：5–45°C
输出：水 + organic_waste + chemical_contaminant 残留
流：StopOnce
```

**为什么惊喜**

- 最清的水可能最“化学”；过量比欠量更危险。
- 同一瓶水：游客不测、批量买家带试纸、拾荒者喝了拉肚子。
- 反应器内壁的氯垢会污染下一批纯水。
- 它不是“净水器”，而是“让你决定这瓶水卖给谁”的反应器。

**必备前置**

```text
水质等级 / 客户试纸 / 价值出口
```

没有这些，氯洗只是一个把 `microbe` 减小的数字。

**验收**

```text
AC-CHLOR-1
Given: 450 mL 脏水（microbe + chemical_contaminant），1 剂量氯
When: 经过氯化器
Then: microbe 归零，水级达到基础水；顾客按基础水价成交

AC-CHLOR-2
Given: 2 剂量氯
When: 经过
Then: 水更清但余氯残留，水级下降；带试纸的顾客拒绝

AC-CHLOR-3
Given: 半剂量
When: 经过
Then: microbe 残留；拾荒者购买后第二天手note 肚子疼/退货
```

---

### 4.3 芬太前处理：稳定剂是锁

```text
第一步：methylol + acid → stabilizing_agent 凝聚成 debris
第二步：过滤掉 debris
第三步：+ reducing_agent，110–130°C → fanta 前体
最终：原版蒸发器/成型机 → 芬太片
```

**为什么惊喜**

- 直接加热 `methylol + reducing_agent` **什么都不发生**；“明显的配方”是错的。
- 稳定剂先变成 `debris`；不过滤会堵/降级。
- 110–130°C 才变紫；超过 130°C 衰减。
- 收率低（约 10%），每毫升极贵。
- 形态就是杀意：片剂天然低于致死线，液体装瓶可能致死；卖片还是卖液是玩家的道德选择。

**设计边界**

```text
不新增 fanta 配方
只做“脱稳定剂 / 过滤 / 还原”这条原版没有的在线前处理
最终产品继续走原版化学机器
```

这样避免“第二套化学引擎”，也保留原版的价值出口。

**验收**

```text
AC-FANTA-1
Given: methylol + reducing_agent，120°C，无酸预处理
When: 经过反应器
Then: 不产生 fanta；状态显示“被抑制 / 稳定剂未去除”

AC-FANTA-2
Given: 先加酸 → 过滤 debris → 再加还原剂，120°C
When: 经过反应器
Then: 产生 fanta 前体；颜色变紫；收率约 10%

AC-FANTA-3
Given: 反应温度 135°C
When: 经过
Then: fanta 衰减；产物等级下降；顾客抱怨“不够劲”

AC-FANTA-4
Given: 同一批前体，分别做成片剂和装瓶
When: 卖给平民
Then: 片剂不致死，瓶装可能致死；后果可见（赔偿/声望/调查）
```

## 5. 候选反应地图

不必全做。按“玩家动词”分组，避免 15 个孤立配方。

| 原型 | 动词 | 候选反应 | 现有 tag | 优先级 |
|---|---|---|---|---|
| 精炼 | 炼 | 冷萃 / 咖啡因萃取 / 梦魇萃取 | dream_cap_mush, coffee_mush, alcohol | P0 |
| 消毒 | 洗 | 氯洗 / 巴氏灭菌 | microbe, chlorine | P1 |
| 中和 | 删 | 酸 + 碱 → 水 + 矿物 + 热 | acid, base | P1 |
| 过滤 | 滤 | 物理过滤 / 混凝沉淀 | debris, chemical_contaminant | P1 |
| 还原 | 沉 | 重金属 + 还原剂 → 矿物 | heavy_metal, reducing_agent | P1 |
| 稳定 | 稳 | 梦魇提取液 → synaprest | nightmare_extract, stabilizing_agent | P1/P2 |
| 发酵 | 酿 | 糖 + 微生物 → 酒精 + 废物 | sugar, microbe | P2 |
| 分离 | 分 | 酒精/水精馏 | alcohol, wine_extract | P2 |
| 热解 | 烧 | 微塑料 → 化学污染 + 碎屑 | microplastic | P2 |
| 氰化 | 浸 | 重金属 + 氰化物 → 矿物 | heavy_metal, zyanide | P2 |

### 每个阶段只加一个新轴

```text
P0：温度 + 比例
P1：客户检测 + 弹药/过滤 + 中和热
P2：时间/批次 + 多出口 + 危险/声誉
```

每阶段：

```text
≤2 种新液体
≤1 个新顾客群
≤1 个新失败模式
总配方 6–10 个
```

## 6. 技术模型

### 6.1 不新增公开接口

保持：

```csharp
bool IFlowDevice.TryReact(FlowProperties properties)
```

不改：

```text
IFlowDevice
IFlowGrid.GetReactorAt
IFlowNotifier
FlowProperties.Split/Merge/Clone
FlowPropertyRegistry
SaveItemNode
```

### 6.2 一个 device key，多套 reactionSet

```text
items.json:
  device: "chem_reactor"
  reactionSet: "extraction_alcohol"

FlowDeviceCatalog:
  chem_reactor → ChemReactorDevice(ReactionCatalog.GetSet(variant))

ChemReactorDevice:
  TryReact(properties)
    → ReactionEngine.React(set, properties, context)
    → ReactionResult.Applied
```

`reactionSet` 只存在 item 定义里，不落 tag；换集合是内容迁移。

### 6.3 数据 + 内核 + 集合

```text
ReactionDefinition：条件、输入/输出、产率参数、优先级
IReactionKernel：可编译、可单测的数学形状
ReactionSet：有序定义 + 每次撞击上限
ReactionEngine：选择、应用、配平校验
ReactionResult：Applied / Failure / 质量差（内部 struct）
```

P0 三个萃取规则复用现有纯函数作为 kernel；不为每条配方写一个类。

### 6.4 守恒与量化

```text
Logic 内先算 delta → 校验总量 → 再写 FlowProperties
严格守恒，误差 ≤1 µL
输出取整一次，副产物取残差
NaN / 负数 / ∞ → 0
温度直接 Set，不用零质量份 Merge
```

不新增 flow tag；副产物继续留在流源里。

### 6.5 存量 / 弹药盒 / 一次性

P0：

```text
无状态
无充能
无 Exhausted
```

P1：

```text
IFlowDeviceState + DeviceTagStore
单独 tag：FLUXFORGE_REACTOR_CHARGE / USES / PROCESSED_UL
不把状态塞进 FlowStock / FlowPropertyRegistry
Changed → 写状态 → 再 Exhausted
```

### 6.6 多出口

P0/P1 不做。

精馏需要：

```text
SplitDevice.Route virtual 化
或 IFlowFacingAdapterAware + adapter 注入朝向
自定义 StillRouter 发 2 股不同组成
```

这是 P1 后半的独立改动，不要混进 P0。

### 6.7 3×3 反应器

`chem_reactor_top` 的资产是 3×3 十字，但当前框架没有：

```text
邻接检测
共享缓冲
模块插槽
控制器
多方块状态
```

它是一个**独立机器框架**，不是“反应 #4”。

建议：

```text
P0 不做
移除/改名为装饰占位，避免玩家误以为能拼
或者单独立项
```

## 7. 经济与平衡

### 7.1 先解决“价值出口”

当前：

```text
FlowProperties 不含价值
items.json 多数物品没有 value
液体容器价格可能只按体积
产物不一定有客户/机器接收
```

每个配方上线前必须有：

```text
输入价值
输出价值
设备/弹药/热能成本
时间/空间机会成本
需求上限
失败成本
```

### 7.2 三个必须的成本

```text
弹药/催化剂损耗
>80°C 的热能成本
每天/每顾客的需求上限
```

缺一个：

```text
不是印钞机，就是电子表格
```

### 7.3 禁止

```text
1. 万能精华：一种产物卖给所有顾客
2. 零损耗催化剂/溶剂
3. 免费高温
4. 废物直升高价成品
5. 反应+售卖一体机
6. 每种液体一个新顾客
7. 一条反应通吃商店
```

### 7.4 验收

```text
T1 价值账本：量产 Vout/Vin ≤1.35；精炼 ≤2.5；奢侈/非法 ≤5.0
T2 质量守恒：总产出 ≤ 输入 + 0.1%；1 µL 批次不凭空产出
T3 催化剂/热能：溶剂每批损耗 ≥5%；>80°C 热能成本 ≥产出价值 10%
T4 循环/并联：闭环 100 圈不增质量；8 台并联利润/格 ≤1 台的 1.5×
T5 需求/失败：单配方 ≤总营收 40%；≥80% 坏批次为部分/降级结果
```

## 8. 发现与反馈

### 8.1 管子会说话

每个反应必须有：

```text
颜色 / 浊度变化
粒子 / 气泡 / 停顿
装置状态（idle / active / blocked）
文字原因（太冷 / 缺酒精 / 比例不足 / 已耗尽）
残留（内壁膜 / 颜色 / 气味）
```

当前反应格被装置贴图遮住，且只停一帧；至少要加：

```text
装置格闪光/气泡
反应前后流源颜色变化
tooltip “上次：温度不足”
```

### 8.2 配方卡，不是配方树

不做“已解锁 3/10”的图鉴。

```text
游戏内攻略可以教步骤；
店铺教判断：
  这瓶水卖给谁
  冰会稀释
  过量比欠量更危险
  片剂和瓶装是两种命
```

### 8.3 失败是材料

```text
过热 → 植物质 / 降解产物
配比错 → 低等级产物
过滤不净 → 下游堵塞
坏批次 → 仍可卖/倒掉/喂给下一个反应
```

不要静默删除。

## 10. 测试计划（P0 切片）

### 单元

```text
R-01 阈值：低于/等于/高于温度
R-02 质量：1 µL / 1 mL / 1 L；总量误差 ≤1 µL
R-03 非反应：缺酒精、太冷、已耗尽；属性完全不变
R-04 重复经过：同一流源两次经过，结果可预测
R-05 分流/合并：先分后反 vs 先反后分，总量一致
```

### 集成

```text
R-06 FlowManager：命中一次、下一帧离开、false 不截停
R-07 反应 + 路由同格：先反应后路由，路由看到新属性
R-08 两个反应器串联：顺序确定
```

### 实机

```text
1. 新档注册反应器
2. 55°C 咖啡豆糊 + 酒精 → 发射 → 收集 caffeine + plant
3. 45°C 同流源 → 梦帽/梦魇反应，咖啡不反应
4. 无酒精/低温 → 直接穿过，无 tag 变化
5. 读档 → 装置仍在、可再次反应
6. 移动/拿起/排序/出售 → 格表即时更新
7. 两个网格互不影响
8. 0 warning / 0 error，221+ 测试全绿
```

### 手动 smoke

```text
- 发射后 0.5 秒保存 → 读档 → 质量对账
- 装置在网格内/手持耗尽
- 旧档占位物品不变成半坏装置
- 两个反应器串联/并联
- 720p/1080p、中英文 tooltip 不溢出
```

## 11. 待拍板

1. **P0 第一条反应**：冷萃（技术最稳）还是氯洗（语言课最强）？
   推荐冷萃：现有纯函数、无新 tag、一个装置即可验证。
2. **在途物质策略**：提交 / 退还 / 禁止保存？
   推荐先做“保存时退还来源容器”，实现小、可对账。
3. **液体价值**：液体定价还是装置/弹药定价？
   必须先做 Spike；否则反应产物没有经济意义。
4. **原版反应归属**：哪些反应只做原版前处理，不直接产出最终品？
   推荐芬太、梦尘、奥克莫吸都只做前处理，最终交原版机器。
5. **精馏多出口**：P1 是否值得为它改 `SplitDevice`？
   推荐 P1 后半再做；P0/P1 前半用单出口浓缩塔过渡。
6. **3×3 反应器**：移除占位、改名，还是独立立项？
   推荐先移除/改名，避免玩家预期错误。

## 12. 最终建议

```text
不要按“15 个反应装置”推进。

先做：
  1 个 chem_reactor
  3 条萃取规则
  1 条冷萃垂直切片
  0 个新 flow tag
  0 个新 patch

再决定：
  氯洗（需要水质/客户/价值出口）
  芬太前处理（需要酸/过滤/还原/成型机）
  中和/过滤/还原（需要弹药盒状态）
  发酵/精馏/热解（需要批次/多出口/危险系统）
```

一句话：

> **玩家不会为“又一个配方”倒吸一口气，他会为“有人记得我做过什么”倒吸一口气。**
>
> 反应层不是化学系统，是店铺的记忆系统。
