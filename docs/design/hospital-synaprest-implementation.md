# 医院100声望原液任务与统一收货结算

实现范围：薇拉100声望任务开端、提纯提交、完成或放弃、额外周供原料；不包含奥雅后续、赛纳普斯合成路线或成型配方。

## 到访与对白

- 前置：医院合同有效、60声望最高需求完成、声望≥100、原液任务未开始且未拒绝。
- 沿用 `NpcStoryHost.QueueAll` 的开门调度，不新增每日计时器或声望监听补丁。
- 独立来访规则冷却1天，绕过普通薇拉7天冷却；到期送料或取货的日期不邀请。
- 邀请开场优先级270，低于合同终止300、高于旧20/40声望里程碑，避免已经满足条件的邀请被旧里程碑挤走。
- 原句与玩家选项见 `Events/HospitalSynaprest/HospitalSynaprestTexts.cs`；不追加任务外对白。
- 接受后的第一句结束，再赠送初始原液并标记开始；拒绝后播放指定告别并关闭任务。

## 交货流程

收货问候 →（任务进行时）“顺便问一下。”及任务询问 → 提交菜单。

普通提交只做桌面检查、收走合格瓶、累计本次分数、提示“收货分数x/300”，然后“还有吗。”并回到菜单。低浓度、空交货提示后返回菜单。

任务进行时只额外提供“提交塞纳普斯原液。”；当前没有接取后的放弃选项。特殊提交只收100%纯液；不纯瓶、普通货物及流体装置留在桌面。成功时每mL计5分，并立即播放相应任务反馈。累计达到550mL后立即完成任务，菜单切换到不含原液专用提交选项的普通菜单。提交超过目标全部计分，进度不封顶。

初次邀请可以拒绝并永久关闭任务；接取后可搁置，不再提供中途放弃。

“没有库存了” → 根据本次累计量决定零交付/不足交付二次确认 → 确认结束后一次性付款、调整声望、推进收货日期 → 总分/报酬提示 → 普通交货评价（本次有普通提交时）→ 原60声望任务结尾插入 → 告别。

结束与二次确认只结算已经提交的货物，不再次读取桌面。不把桌上未经提交的新增货物算进去。普通与特殊交货共享本次分数；统一套用原300分周目标、60声望1.2倍货款、原声望增减规则。舍入只在整次结算时发生。

完成后普通采购品类增加赛纳普斯，最低浓度100%，基础分5/3，沿用普通纯液权重3，最终每mL恰为5分。没有新增赛纳普斯专用浓度容错。

## 原料

- 初次：原版 `bottled_water`（750mL瓶），赛纳普斯600000µL＋污染6061µL，总量606.061mL，约99%浓度。
- 完成后的每次正常送料额外提供：原版 `small_bottled_water`（450mL瓶），赛纳普斯400000µL＋随机2–21052µL污染，浓度严格大于95%、小于100%。
- 污染每瓶均为淀粉与酸/碱之一，淀粉份额随机，两类污染均非零；酸碱不同时出现。
- 瓶规格证据：`.tmp-decomp/FoodItemDirectory.cs:169`、`:179`。`FlowStock.Write` 写回完整成分，所以复用水瓶不会保留原水成分。

## 状态和判断的必要性依据

本次到访累计对象只有内存字段；没有待结算存档、补偿、重试付款、异常恢复、回滚或重复启动适配。异常结束不恢复本次累计。

跨次任务的开始/初次拒绝/完成/累计纯液量沿用 `PlayerStore.modData`，与原60声望任务一致。它们表示剧情结果，不是待结算账本。

| 判断或行为 | 必要性与具体依据 |
|---|---|
| `HospitalPickupSession.BeginVisit` 清零 | `NpcStoryHost` 保存 `NpcStoryContent`，`StartVisit` 通过 `FindEvent` 重用其中的 `StoryAssembly`，不会每访构造新装配；因此装配构造时创建的session必须每访重置。原 `AcidBuyerTradeSession.BeginVisit` 同样如此；新测试 `ReusedPickupAssemblyResetsVisitTotalsWithoutPersistentAccount` 验证两次正常到访。它不是中断恢复。 |
| 任务进度 `TryGetValue` 缺失时取0 | 首次接取前不存在volume键，首次提交边需要先读取Volume判断是否第一次成功交付；`HospitalSynaprestSubmitEdge.Execute` → `HospitalSynaprestState.Volume` 是实际调用路径。沿用 `HospitalHighestDemandState.Read`，不捕获解析异常，不兼容损坏数据。 |
| `IsTag(LiquidContainerTag)`、排除 `FlowDevice` | 原 `AcidBuyerTrade.TrySellAll` 与 `HospitalContractTrade.Inspect` 均扫描混合物品的后柜台；发射器本身也有液体容器身份。新任务使用同一柜台，不能收走设备。测试 `TaskTakesOnlyPureSynaprestAndLeavesImpureBottlesAndDevices` 实际构造了该情况。 |
| `active<=0` 和 `active==SubstanceTotal` | 分别识别非目标货物与100%纯液，是用户明确的收货规则；后者沿用原最高需求的纯度判定，不增加浮点补偿。 |
| 任务完成前普通检查跳过含赛纳普斯的瓶子 | 初始原料按用户指定混有酸或碱；若只是不注册赛纳普斯品类，原 `Inspect` 仍会把其中少量酸/碱视为低浓度目标并阻断普通交货。`OrdinarySubmissionExcludesQuestRawEvenWhenItContainsAcid` 以这份真实成分验证，故需要排除整瓶。 |
| 特殊提交只在 `accepted.Count>0` 时累计 | 桌面为空、只有其他物品、不纯原液三个明确失败分支均不能产生收货分数提示。测试 `FailedTaskSubmissionsReturnWithoutTakingOrCounting` 覆盖，非假想异常。 |
| `Active` 控制菜单、`Completed` 控制正常收货与周供 | 对应用户明确的任务生命周期。提交到550mL的同一条边先写完成标记，再由 `ResolveNext` 选择普通菜单，不额外添加“再次放弃时阻止”的冗余判断。 |
| 结束时判断累计0分/不足300分 | 用户明确保留的二次确认业务；确认边不扫描桌面、不再收货。 |
| 首次/后续、一次完成/部分完成 | 仅决定用户指定对白，读取累计量与本批成功交付结果；没有额外“感谢已播”持久化字段。 |
| 本次普通货物数量 | 原普通交货评价留到结束；仅特殊提交时不额外重复普通超额感谢。无普通提交即不播放普通评价。 |
| 原料最少2µL污染 | 用户要求每瓶同时有“淀粉＋酸”或“淀粉＋碱”；按整数µL写tag，两类各至少1µL，不能随机到只有一种或100%纯液。 |

原版普通医院顾客交易也能增加声望，依据 `.tmp-decomp/StoreReputation.cs:216`、`:253`；邀请读取当前医院声望，下一次开门时即可被选中，不只监听合同付款。
